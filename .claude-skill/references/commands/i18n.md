# Command: `i18n` — UI String Translation & RTL/LTR

## Purpose
Extract hardcoded UI strings — admin panel labels and default-theme
frontend chrome — into centralized language files, with dynamic
`dir="rtl"`/`dir="ltr"`. This is **UI string translation only**, not
multi-language *content* (translating Pages/Posts themselves): the
source brief explicitly lists multi-language content as a future
extensibility item, architecture-ready via the plugin/event system but
not built now — don't let a request for "add Arabic" quietly turn into
building a full content-translation model.

## When to run it
- The audit finds hardcoded UI strings in Plates layouts/components/
  partials or admin views.
- The project needs (or already has) more than one UI language.
- The user says "add translation", "make the admin bilingual", "add RTL
  support", or runs `i18n`.
- **Always runs last** (Phase 3), after `compo`/`themes`/`admin` are
  stable.

## What it does
1. Scan Plates layouts, components, partials, and every admin view for
   hardcoded UI strings (button labels, nav items, form labels, table
   headers, flash messages) — exclude actual content data (Page/Post
   titles/bodies, which stay in whatever single language the content was
   authored in, per the future-extensibility boundary above).
2. Build `resources/lang/{locale}/*.php` files returning nested arrays,
   keyed by namespace (`admin.users.title`, `auth.loginButton`,
   `frontend.nav.home`).
3. A small `__('admin.users.title')` helper (or Plates' own translation
   mechanism if the project already established one) resolves the
   active locale's string, falling back to a default locale on a missing
   key — log the miss, never render the raw key to users.
4. Active locale stored in session or a user preference (admin) / a
   simple cookie or `Accept-Language`-derived default (frontend) — a
   config-level default when neither is set.
5. `dir="rtl"`/`dir="ltr"` set on `<html>` in both `layouts/frontend.php`
   and `layouts/admin.php`, driven by the active locale.
6. Verify layout doesn't break under RTL in both the admin's data tables
   (`compo`'s `table.php`) and the default theme — the most common
   casualties are column order and icon-direction assumptions.

## Output convention
```
resources/lang/{en,ar}/*.php
```

## Checklist
- [ ] No hardcoded UI string remains in a touched layout/component/
      partial/admin view
- [ ] Content data (Page/Post titles/bodies) was correctly left alone —
      this command didn't drift into content-translation scope
- [ ] Every string routed through the translation helper with a stable,
      namespaced key
- [ ] `dir` set correctly in both admin and frontend layouts
- [ ] RTL verified specifically in `compo`'s shared data table component
- [ ] Missing-key fallback logs rather than rendering the raw key
